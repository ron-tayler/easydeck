# How a plugin travels

[plugin-host.md](plugin-host.md) is the contract a plugin runs against. This
is the rest of its life: where its code lives, what a built one looks like,
how it reaches a user's machine, and what happens when two of them claim the
same name.

Decided in August 2026, while the project is in alpha and means to stay there
until roughly twenty more plugins exist. That number is the point: those
plugins' needs are expected to bend the contract, and bending it is allowed.
`PLUGIN_API_VERSION` is the ratchet — a plugin built against an old contract
is refused with an explanation, and one pull request across the plugins
repository rebuilds every plugin against the new one. Nothing here is a point
of no return, and the two known dents are already visible: events that carry
no state change (the same chat message twice, the same MIDI note), and a
status between `ready` and `error` for a plugin that works partially.

## The plugins repository

A second repository, laid out as a monorepo, one folder per plugin under its
author's folder:

```
easydeck-plugins/
  sdk/                     ← @easydeck/plugin-sdk: the contract's types,
                             definePlugin, and the test bench
  plugins/
    <author>/
      <name>/
        manifest.ts        ← the manifest, in code: the one source of truth
        plugin.json        ← generated from manifest.ts at build; committed,
                             so the registry and the store read it without
                             executing anything
        src/               ← the plugin itself, TypeScript
        icons/  locales/   ← read by the host exactly as today
        package.json       ← its own dependencies, its own tsconfig
  registry/
    index.json             ← generated by CI; the store's whole view of the world
```

Source is always present. The built artifact is not committed — CI builds it,
and what a person reads in the repository is what a person wrote.

The SDK lives here rather than in the main repository, beside the people who
type against it: a plugin author clones one repository and has the types, the
template and twenty worked examples. It is a workspace package, not an npm
one — plugins say `workspace:*` and publishing to a registry is a decision
for the day somebody wants to build a plugin *outside* this repository, not
before. The main repository stays the source of truth for the *contract* —
when it bumps `PLUGIN_API_VERSION`, the SDK and every plugin move in one pull
request here, which is the same argument that made this a monorepo at all.
The placeholder `packages/plugin-sdk` in the main repository retires when
this lands.

This repository starts life as a plain folder, `easydeck-plugins` beside the
checkout, before any GitHub repository exists. Nothing about the layout is
provisional — the folder *is* the repository, minus the remote.

## What a built plugin is

The zip CI attaches to a GitHub Release, and equally the folder the store
unpacks into `plugins/<id>/`:

```
plugin.json                ← manifest as data, plus "main"
main.mjs                   ← the whole plugin, bundled by esbuild
icons/  locales/  assets/
natives/win32-x64/…        ← only where the plugin carries native code
```

One `main.mjs` with dependencies bundled in, because a `node_modules` tree is
a thing that works on the author's machine. Native code is the exception that
cannot be bundled, and it is allowed in exactly two forms:

- **a DLL called through koffi** — how the built-in `hardware` plugin already
  works, no ABI to match;
- **an N-API module** — the one native ABI that is stable across Node and
  Electron alike.

A node-gyp module built against a specific runtime is refused outright. That
rule is cheaper than the support burden of explaining, one user at a time,
why a plugin worked until the app updated its Electron.

The manifest declares `platforms`; the store does not offer a plugin to a
machine it cannot run on.

Settings and secrets stay where they are today — `plugin-settings/` and
`secrets/`, beside the plugins folder and not inside it — so installing,
updating or deleting a plugin never touches what the user configured.

## The registry and the store

CI walks the repository, builds each plugin, zips it, computes its sha256,
and writes two things beside the archive: `registry/index.json` and one
`<id>.json` per plugin.

**The index is a list of rows, not of plugins.** Each entry has the id, the
author, the version, `apiVersion`, the size, the hash, the file to fetch — and
a name, a line of description and one cover reference. That is what a row
draws, and it is all it carries.

**The manifest is a file of its own.** It used to ride inside the index and it
was 97 to 99 per cent of every entry: four plugins made a hundred-kilobyte
index of which one and a half kilobytes was ever drawn, and fifty plugins
would have made a megabyte. Now the index is two kilobytes and the manifest is
fetched for the one plugin somebody opened — and kept for as long as the store
is open, because comparing three plugins means going back and forth between
them. "Look again" is what empties it: that is the one moment the answer could
have changed.

The store lives in the app's settings. The daemon fetches `index.json` — the
daemon rather than the browser window, so there is no CORS and no token in a
renderer — and the card it draws comes entirely from the manifest, which is
data. Nothing is executed to browse.

While the repository is a local folder, the registry source is a path instead
of a URL and a build script plays the part of CI. The index format is the
same from the first day, so going remote later changes where the daemon reads
one file from and nothing else.

Installing is: download, check the hash, unpack into `plugins/`, load.
Updating, in alpha, is a button and not a background process. Uninstalling
removes the folder and leaves the settings, for the person who is about to
reinstall.

One rule is inherited from the decision that killed the shell plugin: **a
profile never installs anything.** A profile that references a missing
plugin's actions gets an offer — "this profile uses obs, install it?" — and
the offer is declined by doing nothing. A document somebody imported must not
be able to reach for code.

## Names, and two plugins with one name

A plugin's id is `<author>.<name>`, where the author part is a short slug the
author chooses once and keeps — ours is `ed`, so the OBS plugin is `ed.obs`
and a key stores `ed.obs.set-scene`. Short by convention rather than a full
name by rule, because the id is the prefix of every action type in every
profile, and `maxursmusic-official.obs.set-scene` is a tax on every document.

The slug in the id is what makes provenance free. A profile is the thing
people share, and a shared profile names the plugins it needs down to the
author *in its own action types* — no extra manifest, nothing to keep in
step. "This profile uses `ed.obs`, install it?" is derived from the document
alone, and it offers the same plugin, never a lookalike that happens to also
be called obs.

Collisions still exist — two authors may pick one slug — and the registry
warns about them at publish time, but the conflict is only ever *resolved*
where it becomes real: at install. One id is one folder and one set of action
types, so two plugins with one full id cannot be installed together;
installing the second says so and asks which one stays. That rule is also
what keeps a deliberate reimplementation possible: a plugin that claims a
departed author's id on purpose slots into existing profiles instead of
orphaning them.

The built-in namespaces are reserved and no author may claim them as a slug:
`easydeck`, `core`, `vars`, `system`, `media`, `deck`, `http`, `hardware`,
`clock` — and `ed`.

Moving a built-in out renames its types — `obs.set-scene` becomes
`ed.obs.set-scene` — and old profiles are rewritten once by `migrateProfile`,
which exists for exactly this kind of debt.

## How it runs

**Now: in the daemon's process.** `installed-plugins` learns to see `main` in
a `plugin.json`, the file is imported, and what it exports registers with
`ActionRegistry` and `PluginRuntime` exactly as a built-in does. The SDK a
plugin builds against — `@easydeck/plugin-sdk` — is the types, a
`definePlugin` helper, and the test bench the built-in plugins already use
privately (a fake host, a fake settings store).

Two consequences are accepted rather than solved, because alpha:

- an ES module cannot be unloaded, so updating a plugin's code takes an app
  restart;
- a native crash in a plugin is a crash of the app.

**Later: a process per plugin.** `PluginHost` was shaped for this before any
of this existed — every call is a request carrying data, never an object of
ours, which is what lets the same contract cross a process boundary without
the plugins changing. When the twenty plugins have stopped bending the API,
the transport changes and the plugins do not.

## Who moves out

Leaving the box: `obs`, `vts`, `soundpad`, `yandex` — all four talk to other
programs, none needs elevated rights, and `yandex` carries a real dependency
(`bonjour-service`), which makes it the test that bundling actually works.

Staying built in: `hardware` (koffi, admin rights, deep in the OS), `media`
(the OS again), and `clock` — small enough that shipping it costs nothing and
universal enough that its absence would be the first thing every new user
notices.

## Writing one

The workflow the SDK owes its authors, in order of need:

1. a plugin folder dropped into `plugins/` by hand loads on restart — this is
   the whole of it at first;
2. a template in the plugins repository: manifest, one action, one variable,
   one test against the fake host;
3. a watch mode that reloads the plugin on rebuild — which arrives with the
   process-per-plugin phase, because that is when reload becomes possible.

## How it is published, and where a store reads from

Two shelves, one format.

**GitHub** is what a user gets. A workflow on every push to `main` builds
every plugin, runs their tests, and attaches the archives *and*
`index.json` to a single release tagged `plugins`, replacing the previous
one. The store fetches
`https://github.com/<owner>/<repo>/releases/latest/download/<name>`, an
address GitHub resolves to the newest release by itself — so publishing is
the whole of deployment. Nothing is committed back, no URL is stored
anywhere, and a public repository needs no token, no API and has no rate
limit, because these are plain file downloads.

**A folder** is what somebody writing a plugin gets: `pnpm build` leaves the
archives in `build/` and the index in `registry/`, and the store reads them
where they lie — no push, no tag, no release.

The two are interchangeable because the index names *files* rather than
places: `ed.obs.easydeck` is resolved under `build/` by one and under a
release by the other. Everything else — listing, downloading, caching,
reading a picture out of an archive — is written once, in
`ArchivePluginSource`.

Which one a build uses is decided in one place, `choosePluginSource`:

1. `EASYDECK_PLUGIN_SOURCE=github` — the published store, whatever else is on
   the machine. For seeing what a user will see.
2. `EASYDECK_PLUGIN_SOURCE=<path>` — that folder.
3. A built plugins repository beside any folder on the way up from the working
   directory. Every level is tried because the program is started from
   different places — the repository root by hand, `packages/app` by its own
   dev script, the install folder in production.
4. GitHub.

It is deliberately not a fallback at run time. A store that quietly changed
shelves when a build went stale would answer a different question each time it
was opened, and "why is my plugin not in the list" would have two possible
causes instead of one.
